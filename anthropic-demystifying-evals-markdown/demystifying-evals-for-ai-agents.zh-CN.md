## 引言

良好的评估（evaluation，简称 eval）能帮助团队更有信心地交付 AI 智能体（agent）。缺少评估时，团队很容易陷入被动应对的循环——问题只有到了生产环境才会暴露，修复一个故障又可能引发其他故障。Eval 能在问题和行为变化影响用户之前让它们显现出来，而且其价值会在智能体的整个生命周期中不断累积。

正如我们在[构建高效智能体](https://www.anthropic.com/engineering/building-effective-agents)一文中所述，智能体会跨越多个轮次运行：调用工具、修改状态，并根据中间结果不断调整。正是这些让 AI 智能体变得实用的能力——自主性、智能和灵活性——也使它们更难评估。

通过内部实践以及与智能体开发前沿客户的合作，我们逐渐掌握了如何为智能体设计更严谨、更实用的 eval。以下方法已经在多种智能体架构和真实部署用例中得到验证。

## 评估的结构

**评估（evaluation，简称 eval）**是针对 AI 系统的一项测试：向 AI 提供输入，再对其输出应用评分逻辑，以衡量是否成功。本文重点讨论可在开发期间运行、无须真实用户参与的**自动化评估（automated eval）**。

**单轮评估（single-turn evaluation）**的结构很直接：一个 prompt、一次响应和一套评分逻辑。对于早期的 LLM，单轮、非智能体式 eval 是主要评估方式。随着 AI 能力不断进步，**多轮评估（multi-turn evaluation）**已愈发常见。

![图 1](images/figure-01.webp)

*在简单的 eval 中，智能体处理一个 prompt，评分器检查输出是否符合预期。在更复杂的多轮 eval 中，编码智能体会获得工具、任务（本例中为构建 MCP server）和环境，执行一个“agent loop”（工具调用与推理），并用实现结果更新环境。随后，评分环节通过单元测试验证这个可运行的 MCP server。*

**智能体评估（agent evaluation）**则更为复杂。智能体会跨越多个轮次使用工具，在环境中修改状态，并边执行边调整——这意味着错误可能传播并不断叠加。前沿模型还可能找到超出静态 eval 边界的创造性解法。例如，Opus 4.5 在解决一道关于预订航班的 [𝜏2-bench](https://github.com/sierra-research/tau2-bench) 题目时，[发现](https://www.anthropic.com/news/claude-opus-4-5)了政策中的一个漏洞。按照 eval 的既定写法，它“失败”了，但实际上却为用户找到了更好的解决方案。

构建智能体评估时，我们采用以下定义：

- **任务（task，也称 problem 或 test case）**是一项具有明确输入和成功标准的单次测试。
- 对任务的每一次尝试称为一次**试验（trial）**。由于模型输出会因运行批次而异，我们会执行多次 trial，以获得更加稳定一致的结果。
- **评分器（grader）**是对智能体表现的某一方面进行打分的逻辑。一个任务可以包含多个 grader，每个 grader 又可包含多项断言（assertion，有时也称为 **check**）。
- **执行记录（transcript，也称 trace 或 trajectory）**是一次 trial 的完整记录，包括输出、工具调用、推理、中间结果及其他所有交互。对于 Anthropic API，它指 eval 运行结束时完整的 messages 数组，其中包含评估期间对 API 的所有调用及其返回的全部响应。
- **结果状态（outcome）**是 trial 结束时环境的最终状态。航班预订智能体可能会在 transcript 末尾说“您的航班已预订”，但 outcome 要看环境的 SQL 数据库中是否确实存在一条预订记录。
- **评估框架（evaluation harness）**是端到端运行 eval 的基础设施。它提供指令和工具，并行运行任务，记录所有步骤，对输出评分，并汇总结果。
- **智能体框架（agent harness，也称 scaffold）**是使模型能够作为智能体采取行动的系统：它处理输入、编排工具调用并返回结果。当我们评估“一个智能体”时，实际评估的是 harness *与*模型协同工作的整体。例如，[Claude Code](https://claude.com/product/claude-code) 是一个灵活的 agent harness；我们曾通过 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 使用其核心原语，构建自己的[长时间运行智能体框架](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
- **评估套件（evaluation suite）**是一组用于衡量特定能力或行为的任务。同一 suite 中的任务通常具有共同的总体目标。例如，客服 eval suite 可能会测试退款、取消和升级处理。

## 为什么要构建评估？

团队刚开始构建智能体时，结合人工测试、[dogfooding（内部试用）](https://en.wikipedia.org/wiki/Eating_your_own_dog_food)和直觉，往往就能取得出人意料的进展。更严格的评估甚至可能看起来只是一项拖慢交付速度的额外负担。但过了早期原型阶段，当智能体投入生产并开始规模化后，不做 eval 的开发方式就会逐渐失效。

转折点往往出现在用户反馈“智能体改完之后感觉更差”时，而团队却像在“盲飞”，除了反复猜测和检查，根本无从验证。没有 eval，调试只能被动进行：等待投诉、手动复现、修复 bug，然后寄希望于其他地方没有出现回归。团队无法区分真正的回归与随机噪声，无法在交付前针对数百种场景自动测试改动，也无法衡量改进幅度。

我们已经多次见证这一过程。例如，Claude Code 最初依靠 Anthropic 员工和外部用户的反馈快速迭代。后来，我们加入了 eval——先覆盖简洁度、文件编辑等范围较窄的领域，再扩展到过度设计等更复杂的行为。这些 eval 帮助我们识别问题、引导改进，并让研究团队与产品团队的协作更加聚焦。配合生产监控、A/B 测试、用户研究等手段，eval 为持续改进规模化后的 Claude Code 提供了重要信号。

在智能体生命周期的任何阶段编写 eval 都有价值。早期，eval 会迫使产品团队明确智能体的成功标准；后期，它们则有助于维持稳定一致的质量基线。

[Descript](https://www.descript.com/) 的智能体帮助用户编辑视频，因此他们围绕成功编辑工作流的三个维度构建 eval：不要破坏现有内容、按我的要求做、并且把事情做好。他们从人工评分演进到使用由产品团队定义标准、并定期通过人工校准的 LLM grader，如今会定期运行两套独立 suite，分别用于质量 benchmark 和回归测试。[Bolt](https://bolt.new/) 的 AI 团队则较晚才开始构建 eval，当时他们已经拥有广泛使用的智能体。在 3 个月内，他们搭建了一套 eval 系统：运行智能体并通过静态分析对输出评分，使用浏览器智能体测试应用，还借助 LLM judge 评估指令遵循等行为。

有些团队会在开发之初创建 eval；另一些团队则在业务规模扩大、缺少 eval 已成为智能体改进瓶颈后才加以补充。Eval 在智能体开发初期尤其有用，因为它能明确编码预期行为。两名工程师阅读同一份初始规格，可能会对 AI 应如何处理边界情况产生不同理解；eval suite 可以消除这种歧义。无论何时建立，eval 都有助于加快开发速度。

Eval 还决定了采用新模型的速度。当更强大的模型发布时，没有 eval 的团队可能需要测试数周；拥有 eval 的竞争者则可以迅速判断模型优势、调整 prompt，并在几天内完成升级。

一旦建立 eval，基线和回归测试也就随之具备：可以在固定任务库上持续跟踪延迟、token 用量、单任务成本和错误率。Eval 还可以成为产品团队与研究团队之间信息带宽最高的沟通渠道，通过定义研究人员可以据此优化的指标来对齐工作。显然，eval 的收益远不止跟踪回归与改进。由于成本在前期清晰可见，而收益要在后续不断累积，人们很容易低估它的复利价值。

## 如何评估 AI 智能体

如今，我们看到多种常见智能体已实现大规模部署，包括编码智能体、研究智能体、计算机操作智能体和对话智能体。每一种智能体都可能应用于众多行业，但其评估技术却大体相通。你无须从零发明一种评估方法。以下章节介绍了多类智能体已经验证有效的技术；可以这些方法为基础，再扩展到自己的领域。

### 智能体评分器的类型

智能体评估通常结合三类评分器：基于代码的 grader、基于模型的 grader 和人工 grader。每个 grader 都会评估 transcript 或 outcome 的某个部分。有效评估设计的一个关键环节，就是为具体工作选择合适的 grader。

基于代码的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| • 字符串匹配检查（精确匹配、正则、模糊匹配等）<br>• 二元测试（fail-to-pass、pass-to-pass）<br>• 静态分析（lint、类型、安全）<br>• Outcome 验证<br>• 工具调用验证（所用工具、参数）<br>• Transcript 分析（轮次数、token 用量） | • 快<br>• 成本低<br>• 客观<br>• 可复现<br>• 易于调试<br>• 可验证具体条件 | • 对不完全匹配预期模式的有效变体十分脆弱<br>• 缺乏细腻判断<br>• 难以评估某些主观性较强的任务 |

基于模型的评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| • 基于 rubric 的评分<br>• 自然语言断言<br>• 成对比较<br>• 基于参考答案的评估<br>• 多 judge 共识 | • 灵活<br>• 可扩展<br>• 能捕捉细微差别<br>• 能处理开放式任务<br>• 能处理自由形式输出 | • 非确定性<br>• 比代码评分成本更高<br>• 需要通过人工 grader 校准以保证准确性 |

人工评分器

| **方法** | **优势** | **劣势** |
| --- | --- | --- |
| • 领域专家（SME）审查<br>• 众包判断<br>• 抽样检查<br>• A/B 测试<br>• 标注者间一致性 | • 金标准质量<br>• 与专家用户的判断一致<br>• 可用于校准基于模型的 grader | • 成本高<br>• 速度慢<br>• 规模化时往往需要大量人工专家参与 |

对于每项任务，可以采用加权评分（多个 grader 的合计分数必须达到阈值）、二元评分（所有 grader 都必须通过），或二者结合的混合方式。

### 能力评估与回归评估

**能力评估或“质量”评估（capability or “quality” eval）**要回答的是：“这个智能体能把哪些事情做好？”这类 eval 的初始通过率应该较低，目标应是智能体尚不擅长的任务，从而为团队提供一个需要攀登的高峰。

**回归评估（regression eval）**要回答的是：“这个智能体是否仍能处理过去会做的所有任务？”其通过率应接近 100%。这类 eval 可以防止能力倒退，因为分数下降就意味着某处出了问题，需要加以改进。团队在通过 capability eval 持续提升能力时，也必须同时运行 regression eval，确保改动没有在其他地方引发问题。

智能体上线并经过优化后，通过率较高的 capability eval 可以“毕业”，转变为持续运行、用于捕捉漂移的 regression suite。曾经衡量“我们究竟能不能做到？”的任务，随后就会转而衡量“我们是否仍能可靠地做到？”

### 评估编码智能体

**编码智能体（coding agent）**像人类开发者一样编写、测试和调试代码，在代码库中导航并运行命令。对现代 coding agent 的有效 eval，通常依赖定义明确的任务、稳定的测试环境，以及针对生成代码的全面测试。

确定性 grader 天然适合 coding agent，因为软件通常很容易评估：代码能否运行，测试能否通过？两个广泛使用的 coding agent benchmark——[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 和 [Terminal-Bench](https://www.tbench.ai/)——都采用这种方法。SWE-bench Verified 向智能体提供热门 Python 仓库中的 GitHub issue，并通过运行测试套件对解决方案评分；只有在修复失败测试、同时不破坏既有测试时，方案才算通过。仅仅一年时间，LLM 在这项 eval 上的成绩就从 40% 提升到了 \>80%。Terminal-Bench 则另辟蹊径：它测试端到端的技术任务，例如从源代码构建 Linux kernel，或训练 ML 模型。

一旦拥有一组用于验证编码任务关键 *outcome* 的通过/失败测试，通常还值得对 transcript*.* 进行评分。例如，基于启发式规则的代码质量检查可以从测试是否通过之外的角度评估生成代码；具有明确 rubric 的模型 grader，则可以评估智能体如何调用工具、如何与用户交互等行为。

**示例：编码智能体的理论评估**

假设有一项编码任务，要求智能体修复一个身份验证绕过漏洞。如下方示例 YAML 文件所示，可以同时使用 grader 和指标来评估这个智能体。

```
task:
  id: "fix-auth-bypass_1"
  desc: "Fix authentication bypass when password field is empty and ..."
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

需要注意，这个示例是为了说明而展示了全部可用 grader 类型。在实践中，编码评估通常依赖单元测试验证正确性，并使用 LLM rubric 评估整体代码质量；只有确有需要时，才会加入额外的 grader 和指标。

### 评估对话智能体

**对话智能体（conversational agent）**会在客服、销售或辅导等领域与用户交互。不同于传统聊天机器人，它们会维护状态、使用工具，并在对话过程中采取行动。虽然 coding agent 和 research agent 也可能包含多轮用户交互，但 conversational agent 有一项独特挑战：交互本身的质量就是评估对象的一部分。有效的 conversational agent eval 通常依赖可验证的最终状态 outcome，以及能够同时捕捉任务完成情况和交互质量的 rubric。与大多数其他 eval 不同，它们往往还需要第二个 LLM 来模拟用户。我们在[对齐审计智能体](https://alignment.anthropic.com/2025/automated-auditing/)中采用了这种方法，通过长时间的对抗性对话对模型进行压力测试。

Conversational agent 的成功可能涉及多个维度：工单是否已解决（状态检查）、是否在少于 10 轮内完成（transcript 约束），以及语气是否得当（LLM rubric）？两个体现这种多维性的 benchmark 是 [𝜏-Bench](https://arxiv.org/abs/2406.12045) 及其后继者 [τ2-Bench](https://arxiv.org/abs/2506.07982)。它们会模拟零售客服、机票预订等领域的多轮交互，其中一个模型扮演用户角色，智能体则处理贴近现实的场景。

  
**示例：对话智能体的理论评估**

假设有一项客服任务，要求智能体为一名情绪受挫的客户办理退款。

```
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent showed empathy for customer's frustration"
      - "Resolution was clearly explained"
      - "Agent's response grounded in fetch_policy tool results"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

与 coding agent 示例一样，这项任务为了说明而展示了多种 grader 类型。在实践中，conversational agent eval 通常使用基于模型的 grader，同时评估沟通质量和目标完成情况，因为许多任务——例如回答问题——可能存在多个“正确”解法。

### 评估研究智能体

**研究智能体（research agent）**负责收集、综合和分析信息，并产出回答或报告等成果。Coding agent 可以通过单元测试获得二元的通过/失败信号，而研究质量只能相对于具体任务来判断。何谓“全面”“资料来源充分”，甚至何谓“正确”，都取决于语境：市场扫描、收购尽职调查和科学报告各自需要不同的标准。

Research eval 面临一些独特挑战：专家可能对综合分析是否全面意见不一；参考内容不断变化，ground truth 也随之转移；更长、更开放的输出则为错误留下了更多空间。例如，[BrowseComp](http://arxiv.org/abs/2504.12516) 这类 benchmark 测试 AI 智能体能否在开放网络的干草堆中找到针——问题被设计成易于验证，却很难求解。

构建 research agent eval 的一种策略是组合多种 grader。Groundedness check 验证论断是否得到检索来源的支持；coverage check 定义高质量答案必须包含的关键事实；source quality check 则确认采用的来源具有权威性，而不仅仅是最先检索到的结果。对于存在客观正确答案的任务（“X 公司第三季度的营收是多少？”），精确匹配即可奏效。LLM 既可以标记缺乏支持的论断和信息覆盖缺口，也可以检查开放式综合分析是否连贯、完整。

由于研究质量具有主观性，基于 LLM 的 rubric 应频繁与人类专家判断进行校准，才能有效评估这类智能体。

### 计算机操作智能体

**计算机操作智能体（computer use agent）**通过与人类相同的界面——屏幕截图、鼠标点击、键盘输入和滚动——与软件交互，而非使用 API 或执行代码。它们可以操作任何具有图形用户界面（GUI）的应用，从设计工具到旧式企业软件。评估这类智能体时，需要让它在真实或沙盒环境中运行、使用软件应用，并检查它是否达成预期 outcome。例如，[WebArena](https://arxiv.org/abs/2307.13854) 测试基于浏览器的任务：通过 URL 和页面状态检查来验证智能体是否正确导航；对于会修改数据的任务，还会验证后端状态（确认订单确实已经提交，而不是只显示了确认页面）。[OSWorld](https://os-world.github.io/) 将此扩展到对整个操作系统的控制，其评估脚本会在任务完成后检查多种 artifact：文件系统状态、应用配置、数据库内容以及 UI 元素属性。

浏览器操作智能体需要在 token 效率和延迟之间取得平衡。基于 DOM 的交互执行迅速，但会消耗大量 token；基于截图的交互速度更慢，却更节省 token。例如，让 Claude 总结 Wikipedia 内容时，从 DOM 中提取文本更高效；而在 Amazon 上寻找新的笔记本电脑保护套时，截图更高效（因为提取完整 DOM 会消耗大量 token）。在 Claude for Chrome 产品中，我们开发了 eval，用于检查智能体是否会针对不同情境选择合适的工具。这使我们能够更快、更准确地完成浏览器任务。

### 如何看待智能体评估中的非确定性

无论哪类智能体，其行为都会因运行批次而异，因此评估结果比乍看之下更难解读。每项任务都有自己的成功率——可能一项是 90%，另一项是 50%——而且同一任务在一次 eval 运行中通过，下一次却可能失败。有时，我们真正想衡量的是智能体完成某项任务的*成功频率*（即成功 trial 所占的比例）。

有两个指标可以捕捉这种细微差别：

[**pass@k**](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf) 衡量智能体在 *k* 次尝试中至少得到一个正确解的概率。随着 *k* 增大，pass@k 分数会上升：尝试次数越多，至少成功一次的概率就越高。50% pass@1 表示模型在第一次尝试时，就能成功完成 eval 中一半的任务。在编码领域，我们往往最关心智能体能否一次找到解法，也就是 pass@1；而在其他情形下，提出多个方案也完全合理，只要其中一个可行即可。

[**pass^k**](https://arxiv.org/abs/2406.12045) 衡量 *k* 次 trial **全部成功**的概率。随着 *k* 增大，pass^k 会下降，因为要求更多次 trial 保持一致成功，标准也就更加严苛。如果智能体每次 trial 的成功率为 75%，并运行 3 次，那么三次全部通过的概率为 (0.75)³ ≈ 42%。该指标对面向客户的智能体尤其重要，因为用户期望它每次都能可靠工作。

![图 3](images/figure-03.webp)

*随着 trial 次数增加，pass@k 与 pass^k 逐渐分化。k=1 时，两者完全相同（都等于单次 trial 的成功率）；到 k=10 时，它们讲述的故事恰好相反：pass@k 逼近 100%，而 pass^k 降至 0%。*

两个指标都有价值，具体选用哪一个取决于产品需求：对于只需成功一次的工具，使用 pass@k；对于一致性至关重要的智能体，则使用 pass^k。

## 从零到一：打造卓越智能体评估的路线图

本节给出我们经过实践检验的建议，说明如何从没有 eval 起步，逐渐构建出值得信赖的 eval。可以将其视为 eval 驱动的智能体开发路线图：尽早定义成功，清晰衡量成功，并持续迭代。

### 为初始评估数据集收集任务

**第 0 步：尽早开始**

我们常看到团队因为以为需要数百个任务，而一再推迟构建 eval。事实上，从真实故障中提取 20～50 个简单任务，就是一个很好的起点。毕竟，在智能体开发早期，对系统的每一项改动通常都会产生清晰可见的影响；较大的效应量意味着较小的样本规模已经足够。更成熟的智能体可能需要规模更大、难度更高的 eval，才能检测出更小的变化，但在起步阶段最好采用 80/20 原则。拖得越久，eval 越难构建。早期，产品需求可以自然转化为测试用例；等得太久，就只能从已经上线的系统中逆向推导成功标准。

**第 1 步：从已有的人工测试开始**

从开发过程中已经执行的人工检查入手——包括每次发布前验证的行为，以及最终用户经常尝试的任务。如果产品已经上线，就查看 bug tracker 和客服队列。将用户报告的故障转换为测试用例，可以确保 suite 反映真实使用情况；按照用户影响程度确定优先级，则能帮助你把精力投入最有价值的地方。

**第 2 步：编写无歧义的任务及参考解法**

确保任务质量比想象中更难。高质量任务应该让两名领域专家在彼此独立的情况下得出相同的通过/失败结论。他们自己能完成这项任务吗？如果不能，任务就需要进一步完善。任务规格中的歧义会变成指标里的噪声；基于模型的 grader 标准也同样如此：模糊的 rubric 会产生不一致的判断。

每项任务都应当能被一个正确遵循指令的智能体完成，这一点有时很微妙。例如，对 Terminal-Bench 的审计发现：如果任务要求智能体编写脚本，却没有指定文件路径，而测试又假定脚本位于某个特定路径，那么智能体可能会在自身毫无过错的情况下失败。Grader 检查的所有内容都应在任务描述中清晰说明；智能体不应因规格含糊而失败。对于前沿模型，多次 trial 后仍为 0% 的通过率（即 0% pass@100），通常意味着任务本身有问题，而不是智能体能力不足；这时应重新核查任务规格和 grader。为每项任务创建参考解法也很有帮助：即一个已知可行、能通过所有 grader 的输出。它既能证明任务确实可解，也能验证 grader 配置正确。

**第 3 步：构建均衡的问题集**

既要测试某种行为*应该*发生的情况，也要测试它*不应该*发生的情况。单边 eval 会造成单边优化。例如，如果只测试智能体在应该搜索时是否会搜索，最终可能得到一个几乎什么都要搜索的智能体。应尽量避免[类别不均衡（class-imbalanced）](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的 eval。我们在为 [Claude.ai](http://claude.ai/redirect/website.v1.e5b189ee-3730-4d5e-ac2c-be230348275a) 的 web search 构建 eval 时对此有过切身体会。难点在于：既要防止模型在不该搜索时搜索，又要保留它在适当场景中开展深入研究的能力。团队构建了覆盖两个方向的 eval：模型应该搜索的查询（例如查询天气），以及应利用已有知识直接回答的查询（例如“Apple 是谁创立的？”）。要在触发不足（该搜索时不搜索）与过度触发（不该搜索时却搜索）之间取得平衡并不容易，需要对 prompt 和 eval 进行多轮改进。随着更多示例问题出现，我们会继续将它们加入 eval，以提高覆盖率。

### 设计评估框架和评分器

**第 4 步：用稳定环境构建稳健的 eval harness**

Eval 中的智能体必须与生产环境中的智能体大致以相同方式工作，环境本身也不应引入额外噪声。每次 trial 都应该从干净环境开始，彼此“隔离”。不同运行之间不必要的共享状态（残留文件、缓存数据、资源耗尽）可能导致相关性故障；这些故障源于基础设施不稳定，而非智能体表现。共享状态也可能人为抬高成绩。例如，我们在一些内部 eval 中观察到，Claude 会查看前几次 trial 的 git 历史，从而在某些任务中取得不公平的优势。如果多项不同 trial 都因环境中的同一限制（例如 CPU 内存不足）而失败，那么它们受到同一因素影响，便不再相互独立，eval 结果也就无法可靠地衡量智能体表现。

**第 5 步：审慎设计评分器**

如前所述，卓越的 eval 设计需要为智能体和任务选择最合适的 grader。我们的建议是：能用确定性 grader 时优先使用；确有必要或需要更高灵活性时使用 LLM grader；再审慎地使用人工 grader 进行补充验证。

人们通常会本能地检查智能体是否严格遵循特定步骤，例如是否按照正确顺序执行一系列工具调用。我们的经验表明，这种方法过于僵化，会产生异常脆弱的测试，因为智能体经常能找到 eval 设计者未曾预料的有效路径。为了避免无谓地惩罚创造性，更好的做法往往是评估智能体产出了什么，而不是它采取了怎样的路径。

对于包含多个组成部分的任务，应设置部分得分**。** 一个客服智能体如果正确识别了问题并验证了客户身份，却未能办理退款，仍然明显优于一开始就失败的智能体。结果必须能体现这种连续的成功程度。

模型评分通常需要细致迭代，才能验证其准确性。应让 LLM-as-judge grader 与人类专家紧密校准，从而有把握确认人工评分与模型评分之间只有很小偏差。为避免幻觉，应为 LLM 留出无法判断时的退路，例如指示它在信息不足时返回“Unknown”。还可以为任务的每个维度建立清晰、结构化的 rubric，再用相互独立的 LLM-as-judge 分别为各维度评分，而不是用一个 LLM 一次评估所有维度。系统足够稳健后，只需偶尔进行人工审查即可。

有些 eval 存在隐蔽的失败模式：即使智能体表现良好，也可能因评分 bug、agent harness 限制或歧义而无法完成任务，导致低分。即使经验丰富的团队也可能漏掉这些问题。例如，[Opus 4.5 最初在 CORE-Bench 上只得到 42%](https://x.com/sayashk/status/1996334941832089732?s=46&t=c5pEvnVdVbMkcR_rcCHplg)，后来 Anthropic 研究人员发现了多个问题：僵化的评分会在期望“96.124991…”时惩罚“96.12”；任务规格存在歧义；随机性任务无法精确复现。修复 bug 并改用限制较少的 scaffold 后，Opus 4.5 的得分跃升到 95%。同样，[METR 也发现](https://x.com/metr_evals/status/2001473506442375645?s=46)，其 time horizon benchmark 中有多项任务配置错误：任务要求智能体优化到某个明确给出的分数阈值，评分却要求必须超过该阈值。这种设置惩罚了 Claude 这类遵循指令的模型，反而让忽略既定目标的模型得到更高分。仔细复核任务和 grader 有助于避免此类问题。

还应确保 grader 能抵御绕过或攻击。智能体不应能够轻易在 eval 中“作弊”。任务和 grader 的设计应保证：要想通过，就必须真正解决问题，而不能利用意料之外的漏洞。

### 长期维护和使用评估

**第 6 步：检查执行记录**

如果不阅读大量 trial 的 transcript 和评分结果，就无法知道 grader 是否正常工作。在 Anthropic，我们投入资源开发了查看 eval transcript 的工具，也会定期花时间阅读记录。任务失败时，transcript 可以告诉你：是智能体确实犯了错误，还是 grader 拒绝了一个有效解法。它通常还能揭示智能体和 eval 行为中的关键细节。

失败应该让人觉得公平：能够清楚看出智能体错在哪里、为什么错。当分数迟迟没有提升时，我们必须确信原因在于智能体表现，而不是 eval 本身。阅读 transcript，正是验证 eval 是否真正衡量了重要事项的方法，也是智能体开发的一项关键技能。

**第 7 步：监控 capability eval 饱和**

达到 100% 的 eval 可以跟踪回归，却无法为进一步改进提供信号。当智能体通过所有可解任务、再无提升空间时，就出现了**评估饱和（eval saturation）**。例如，SWE-Bench Verified 的分数在今年初为 30%，如今前沿模型已在 \>80% 附近接近饱和。随着 eval 逼近饱和，进展也会放缓，因为只剩下最困难的任务。这可能造成误导：能力大幅提升，分数上却只表现为很小的增长。例如，代码审查初创公司 [Qodo](https://www.qodo.ai/) 起初对 Opus 4.5 印象平平，因为他们的 one-shot coding eval 没能捕捉它在更长、更复杂任务上的提升。为此，他们开发了新的 agentic eval framework，从而更清晰地呈现进展。

原则上，在有人深入研究 eval 的细节并阅读部分 transcript 之前，我们不会照单全收 eval 分数。如果评分不公、任务含糊、有效解法受到惩罚，或 harness 限制了模型，就应该修订 eval。

**第 8 步：通过开放贡献与维护，长期保持评估套件的健康**

Eval suite 是一种活的 artifact，需要持续关注并明确归属，才能长期保持价值。

在 Anthropic，我们尝试了多种 eval 维护方式。实践证明最有效的方法是：组建专门的 eval 团队负责核心基础设施，同时由领域专家和产品团队贡献大多数 eval 任务，并自行运行评估。

对于 AI 产品团队而言，负责并持续迭代 eval 应该像维护单元测试一样成为日常工作。团队可能在某项 AI 功能上浪费数周——它在早期测试中似乎“能用”，却无法满足那些没有明说的预期，而设计良好的 eval 原本可以及早暴露这些问题。定义 eval 任务，是检验产品需求是否已经具体到足以开始构建的最佳方式之一。

我们建议践行 eval-driven development：在智能体尚不能实现规划能力之前，就用 eval 定义这些能力，再不断迭代，直至智能体表现良好。在内部，我们经常构建今天只能做到“足够好”的功能，但这些功能其实是在押注几个月后的模型能力。初始通过率较低的 capability eval 可以让这件事变得可见。新模型发布后，运行 suite 就能迅速揭示哪些押注获得了回报。

最接近产品需求和用户的人，最适合定义成功。以当前的模型能力，产品经理、客户成功经理或销售人员都可以使用 Claude Code，以 PR 形式贡献 eval 任务——让他们参与进来！更进一步，应主动为他们创造参与条件。

## 评估如何与其他方法配合，形成对智能体的整体认识

自动化评估可以让智能体执行数千项任务，无须部署到生产环境，也不会影响真实用户。但这只是理解智能体表现的众多方式之一。完整图景还包括生产监控、用户反馈、A/B 测试、人工 transcript 审查和系统化人工评估。

理解 AI 智能体表现的方法概览

| 方法 | 优势 | 劣势 |
| --- | --- | --- |
| **自动化评估<br>***在没有真实用户参与的情况下以程序方式运行测试* | • 迭代更快<br>• 完全可复现<br>• 不影响用户<br>• 可在每次 commit 时运行<br>• 无须部署到生产环境，即可规模化测试各种场景 | • 前期构建投入较大<br>• 随着产品和模型演进，需要持续维护以避免漂移<br>• 如果与真实使用模式不符，可能造成虚假的信心 |
| **生产监控<br>***跟踪线上系统中的指标和错误* | • 大规模揭示真实用户行为<br>• 捕捉合成 eval 遗漏的问题<br>• 提供智能体实际表现的 ground truth | • 被动响应；问题会在被发现前先影响用户<br>• 信号可能噪声较大<br>• 需要投入建设观测能力<br>• 缺乏评分所需的 ground truth |
| **A/B 测试<br>***使用真实用户流量比较不同方案* | • 衡量实际用户 outcome（留存、任务完成）<br>• 控制混杂因素<br>• 可扩展且系统化 | • 速度慢；需要数天或数周才能达到统计显著性，且必须有足够流量<br>• 只能测试已经部署的改动<br>• 如果无法彻底审查 transcript，就很难解释指标变化背后的“原因” |
| **用户反馈<br>***点踩或 bug 报告等显式信号* | • 暴露未曾预料的问题<br>• 附带来自真实人类用户的实际案例<br>• 反馈往往与产品目标相关 | • 稀疏且存在自我选择偏差<br>• 偏向严重问题<br>• 用户很少解释失败的*原因*<br>• 无法自动化<br>• 主要依靠用户发现问题，可能带来负面用户影响 |
| **人工执行记录审查<br>***由人阅读智能体对话* | • 帮助建立对失败模式的直觉<br>• 捕捉自动检查遗漏的细微质量问题<br>• 有助于校准何谓“好”，并掌握具体细节 | • 耗时<br>• 无法规模化<br>• 覆盖不一致<br>• 审查疲劳或审查人员差异会影响信号质量<br>• 通常只能提供定性信号，而非清晰的量化评分 |
| **系统化人工研究<br>***由受过训练的评分人员对智能体输出进行结构化评分* | • 来自多名人工评分人员的金标准质量判断<br>• 能处理主观或含糊的任务<br>• 为改进基于模型的 grader 提供信号 | • 成本相对较高，周转较慢<br>• 难以频繁开展<br>• 评分者之间的分歧需要协调<br>• 复杂领域（法律、金融、医疗）需要人类专家开展研究 |

这些方法分别对应智能体开发的不同阶段。自动化 eval 在发布前和 CI/CD 中尤其有用，可以在每次智能体改动或模型升级时运行，充当抵御质量问题的第一道防线。生产监控在发布后介入，用于检测分布漂移以及未曾预料的真实世界故障。拥有足够流量后，A/B 测试可用于验证重大改动。用户反馈和 transcript 审查则是持续弥补空白的实践：不断分流处理反馈，每周抽样阅读 transcript，并按需深入调查。系统化人工研究应留给校准 LLM grader，或者评估那些以人类共识作为参考标准的主观输出。

![图 5](images/figure-05.png)

*与安全工程中的[瑞士奶酪模型（Swiss Cheese Model）](https://en.wikipedia.org/wiki/Swiss_cheese_model)一样，任何单一评估层都无法捕捉全部问题。组合使用多种方法后，从一层漏过的故障便会被另一层捕获。*

最高效的团队会组合使用这些方法：以自动化 eval 快速迭代，以生产监控获取 ground truth，再通过定期人工审查完成校准。

## 结论

没有 eval 的团队会深陷被动应对的循环——修复一个故障，又制造另一个故障，而且无法区分真正的回归与噪声。尽早投入 eval 的团队则会迎来相反的局面：故障变成测试用例，测试用例阻止回归，指标取代猜测，开发由此加速。Eval 为整个团队树立了一座目标明确的山峰，把“感觉智能体变差了”转化为可采取行动的问题。它的价值会不断复利增长，但前提是将 eval 视为核心组成部分，而不是事后才想起的补充。

不同类型智能体的具体模式各异，但本文所述的基本原则始终不变。尽早开始，不必等待完美的 suite。从实际遇到的失败中提取真实任务。定义无歧义、稳健的成功标准。审慎设计 grader，并组合多种类型。确保问题对模型而言足够困难。持续迭代评估，提高信噪比。一定要阅读 transcript！

AI 智能体评估仍是一个新兴且快速演进的领域。随着智能体承担更长的任务、在 multi-agent system 中协作，并处理越来越主观的工作，我们也需要不断调整评估技术。随着认识不断深入，我们会继续分享最佳实践。

## 附录：Eval framework

多种开源及商业 framework 都能帮助团队实现智能体评估，无须从零构建基础设施。具体选择取决于智能体类型、现有技术栈，以及需要离线评估、生产可观测性，还是两者兼备。
  
[Harbor](https://harborframework.com/) 专为在容器化环境中运行智能体而设计，提供跨云服务商大规模运行 trial 的基础设施，以及定义任务和 grader 的标准格式。Terminal-Bench 2.0 等热门 benchmark 通过 Harbor registry 分发，因而可以轻松地将成熟 benchmark 与自定义 eval suite 一起运行。
  
[Braintrust](https://www.braintrust.dev/) 是一个结合离线评估、生产可观测性和实验跟踪的平台，适合既需要在开发期间迭代、又需要在生产环境监控质量的团队。它的 `autoevals` 库提供用于事实性、相关性及其他常见维度的预构建 scorer。
  
[LangSmith](https://docs.langchain.com/langsmith/evaluation) 提供 tracing、离线与在线评估以及数据集管理，并与 LangChain 生态系统深度集成。[Langfuse](https://langfuse.com/) 提供类似能力，是一种可自行托管的开源替代方案，适用于存在数据驻留要求的团队。

[Arize](https://arize.com/) 提供 Phoenix——一个用于 LLM tracing、调试以及离线或在线评估的开源平台——以及 AX；AX 是在 Phoenix 基础上扩展了规模化、优化和监控能力的 SaaS 产品。
  
许多团队会组合使用多种工具、自行构建 eval framework，或仅以简单的评估脚本作为起点。我们的经验是，framework 固然能有效加速进展、统一规范，但它的价值取决于其中运行的 eval 任务质量。通常最好的做法是迅速选定适合工作流的 framework，再把精力投入 eval 本身，持续迭代高质量的测试用例和 grader。
